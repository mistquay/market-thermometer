# 平台规划（草案 v0.1，2026-11-25）

> 目标：从“市场温度计”演进为**投研与分析平台**，后续接入更多数据源，并逐步支持模拟交易和实盘自动下单。
> 原则：**核心尽量小，其余都做成插件**。本文是方向性规划，具体阶段开工前再细化设计。

---

## 1. 核心与插件的边界

### 1.1 核心（不做成插件）

| 模块 | 职责 |
|---|---|
| 数据存储 | 我们自己的数据：证券主数据、日线、净值、指标时间序列、事件；多来源并存，带来源与抓取时间 |
| 插件宿主 | 插件注册、配置、生命周期、健康检查、调用超时与限流、能力声明 |
| 任务调度 | 定时任务、后台任务、进度与日志、失败重试、幂等 |
| Web 外壳 | 登录鉴权、导航、通用组件（表格、图表、表单）；插件可以注册页面或面板 |
| 审计 | 关键操作日志（参数生效、交易指令、配置变更），不可删改 |
| 风控底座 | 交易前置检查的统一入口（规则由插件或配置提供，执行由核心保证） |

### 1.2 插件类型

| 类型 | 接口（示意） | 现有实现 |
|---|---|---|
| 指标数据源 | `Fetch(metric, from, to) → points` | 东财、中证；外部示例 csv_source（Python） |
| 证券日线源 | `ListStocks()`、`Bars(code, from, to)` | stockdb、腾讯 |
| 基金净值源 | `ListFunds()`、`NAV(code, from)` | 东财 |
| 派生指标 / 因子 | 输入本地数据，输出时间序列 | 市场广度 `breadth_ma200`（`internal/derived`） |
| 策略 / 信号 | 输入指标，输出信号与目标仓位 | 市场温度计 `thermometer`（`internal/strategy`） |
| 通知 | `Send(message)` | 钉钉、飞书、企业微信、Telegram；外部插件可扩展 |
| 交易通道 | 下单、撤单、查持仓与资金、成交回报 | 只设计接口（`docs/plugin-protocol.md` §5），未实现 |
| 页面扩展 | 声明菜单项与前端组件 | 无 |

### 1.3 插件形态（分阶段）

1. **内置 Go 插件**（现状）：编译进二进制，用 `init()` 注册。性能好、部署简单，适合核心团队维护的常用插件。
2. **外部进程插件**（下一步）：插件是独立程序，可以用任何语言（如 Python 的 akshare、券商的 QMT 接口），通过标准输入输出或本机 HTTP 走 JSON-RPC 协议。
   - 每个插件附一份清单文件，声明名称、版本、类型、能力和配置字段。Web 根据配置字段自动生成配置表单。
   - 只能在 `config.yaml` 中启用，Web 不能新增或修改可执行路径（等同于执行任意命令）。
   - 核心负责超时、重启和资源隔离；插件崩溃不影响核心。
3. **不使用 Go 原生 `plugin` 包**：它不支持 Windows，且对编译环境一致性要求严格。

### 1.4 数据层演进

- 现状 SQLite 约 800MB，对单机够用。数据量继续增长（分钟线、财务、多市场）时，再评估时序数据迁移到 DuckDB / Parquet 或 PostgreSQL + TimescaleDB；存储接口先保持稳定，迁移对插件透明。
- **证券主数据**统一管理：代码、名称、类别（股票 / 场内基金 / 场外基金 / 指数 / 债券）、上市退市日期、所属指数与行业。
- **数据质量**作为核心能力：多来源交叉核对、缺口检测、事后修正重拉（本次已发现 stockdb 当日为临时数据、个别股票有缺口）。

## 2. 阶段规划

| 阶段 | 内容 | 前置条件 |
|---|---|---|
| **P1 温度计可用** | 信号规则校准（已有开关与分层持仓）；M5 推送（4 个渠道）、调度、部署；数据质量页（交叉核对、缺口） | 回测在样本外跑赢估值档基线，才开启实盘提醒 |
| **P2 插件化重构** | 插件清单与外部进程协议；插件管理页；温度计、市场广度迁移为插件；通知插件化 | P1 稳定运行 |
| **P3 投研功能** | 自选股票 / 基金组合；行情与净值图；组合分析（收益、回撤、相关性、归因）；财务与估值数据；研究笔记 | P2 |
| **P4 模拟交易** | 订单、持仓、资金模型；模拟撮合（按收盘价、滑点、手续费）；策略产出目标仓位 → 生成订单 | P3 |
| **P5 实盘交易** | 券商交易插件；人工确认下单 → 小额自动 → 全自动，逐级放开 | P4 跑通 ≥ 3 个月且对账一致 |
| **P6 多市场** | 美股（FRED、CBOE 等）、港股；市场定义与交易日历插件化 | 可与 P3–P5 并行 |

## 3. 交易相关的安全要求（P4 / P5 开工前必须落实）

- **合规**：国内程序化交易需按券商要求报备（参见证监会程序化交易管理相关规定），接入前和券商确认可用的接口与报备流程（如 QMT / PTrade 等券商提供的终端）。
- **分级放权**：模拟盘 → 人工逐笔确认 → 单笔 / 单日金额上限内自动 → 全自动；每一级都要有足够的运行记录才升级。
- **风控（核心强制执行，插件不能绕过）**：单笔与单日金额上限、单标的仓位上限、交易时段、标的黑白名单、委托频率限制；**一键熔断**（停止所有自动下单）。
- **对账**：每日核对本地订单、成交、持仓与券商回报，不一致时自动停止自动交易并告警。
- **凭证**：券商账号与密钥只存在本机（系统密钥库或加密文件），不经过 Web、不写入数据库和日志；交易相关操作需要二次确认。
- **审计**：每一笔信号 → 订单 → 成交的链路可追溯，参数版本与当时数据快照可回放。

## 4. 已确认（2026-11-25）

1. 阶段顺序按 P1 → P6 执行，P2 插件化重构排在 P3 投研之前。
2. P3 投研优先级：组合分析 → 行情图 → 财务数据。
3. 券商与交易终端尚未确定：P4 模拟交易的模型与券商无关；P5 只设计交易插件接口，不实现；外部进程插件协议优先支持 Python。
